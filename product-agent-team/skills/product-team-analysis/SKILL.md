# 产品分析输出

本 Skill 面向资料调研与比较分析；真实应用交互走查使用 [product-audit](../product-audit/SKILL.md)。澄清与交付节奏沿用 [共享工作流](../../workflow.md)，事实、推导与回写资格沿用 [轻量产品模型与回写](../../project-memory-rules.md#轻量产品模型与回写)。

将零散资料转换为内部决策材料。核心要求是：先明确调研问题和决策用途，再确定盘点范围；事实边界先于观点，结论先于过程，主线先于清单，产品能力先于宣传口号。产品类型只影响调研维度，不自动决定分析框架；普通业务系统不强行套用 Agent、MCP 或 Skills 结构。

## 输出目标

根据用户要求选择交付形式：

- 只要分析结论：输出短文或 Markdown。
- 需要汇报材料：输出结论优先的 Markdown，必要时同步生成 HTML。
- 需要全景图或关系图：在正文中加入一张回答明确问题的结构化图，不用装饰性插图替代关系表达。
- 用户给出已有文档：按[事实来源与采纳](../../project-memory-rules.md#事实来源与采纳)确定有效版本和范围，区分已确认依据与工作草稿；修改时间仅作检索线索。只有本轮要求修订时才修改指定工作稿，不以较新的草稿替代已确认规则，不重建已被取代的内容。

默认面向内部汇报，正文不展示调研过程、搜索过程、验证步骤或模型推理。来源、官网链接和必要截图放在附录或表格的“来源”列中，以便复核但不抢占结论层级。

## 工作流程

### 1. 确定分析任务

先使用[产品分析前置判断](../../workflow.md#产品分析前置判断)的共同标准，再按下列调研维度细化；不因进入调研方法而省略真实问题、关键约束或重复询问已知信息。

从当前要求、同项目有效上下文和已提供资料中确定以下内容。简单分析在内部理清即可；复杂调研可用简短计划说明范围，不强制单独生成计划页或等待批准：

- **决策问题与受众**：支持现状盘点、竞品比较、接入判断、建设建议或其他明确判断。
- **分析主体**：产品、版本、企业版/个人版、部署形态和适用时间；区分主体与对标对象。
- **重点维度**：按决策用途选择功能、场景、对象、流程、数据、权限、生态、交付、运营或商业模式。
- **资料与产出**：已有资料、可核实来源、事实口径及用户所需格式；区分当前能力、规划和建议。

资料能核实的未知可继续查证；需要用户决定且影响当前结论的缺口按共享工作流处理，不停止其他独立资料收集。主体本身无法识别时先询问主体，不能靠行业印象替用户选产品。已明确的范围直接使用，不为填满维度再次访谈。

用户要求“严格盘点”时，只将证据足够的具体能力写为已支持；用户要求建议时，可以给出有依据的推断并标明边界。普通业务、硬件、内容或线下产品按真实任务组织，不自动添加 Agent、MCP 或 Skills 章节。

### 2. 建立产品与归属边界

复杂盘点可先整理能力台账；少量能力直接在正文表格中记录。字段按分析任务选择，保留能够区分能力、归属、边界和来源的信息：

| 字段 | 记录内容 |
|---|---|
| 场景 | 聊天、会议、文档、邮件、日程、待办、项目、研发、人力、财务、法务等 |
| 产品/系统 | 具体产品名，不用“腾讯办公”“HR 系统”等泛称代替 |
| 产品状态 | 原生能力、已接入插件/连接器、API、MCP、Skill、消息入口或目录项 |
| 已确认动作 | 可查询、创建、编辑、更新、发送、管理或生成的具体对象 |
| 归属 | 官方生态、目标产品能力、第三方连接器、企业自建能力或待确认 |
| 边界 | 未展示、受企业规模限制、需授权、仅入口型或由源系统负责的部分 |
| 来源 | 具体页面、截图、产品文档或本地界面 |

产品目录出现某个名称，只能说明存在目录项；不能自动说明官方开发、官方授权、开放平台关系或完整数据访问。开发者将开放接口包装成插件、连接器或 MCP 后接入目标产品，也应标记为第三方能力，不能归入原产品生态的官方接入。

### 3. 严格确认能力状态

使用以下判断优先级：

1. 产品界面展示的具体动作。
2. 官方文档写明的具体动作。
3. 可直接读取的 MCP 工具名称、参数和返回对象。
4. 官方产品开放平台写明的接口能力。
5. 产品名、场景名或宣传语，只能作为待核实线索。

不要把以下内容写成已支持：

- 仅因为某个源系统存在开放 API，就声称目标产品已能查询所有业务数据。
- 仅因为连接器名为“企业微信”，就声称支持考勤、审批、通讯录、完整聊天记录或组织权限。
- 仅因为某个市场或 Hub 可发现服务，就声称服务已经安装、授权或可执行。
- 仅因为 Bot、Webhook 或消息入口能接收任务，就声称已经打通聊天历史、业务对象或持续状态。
- 仅因为某个局部工具可以处理单一文件或字段，就声称具备完整业务系统能力。

将支持程度与能力归属分开表达，按证据使用以下标签：

- **已支持**：来源明确写出适用版本中的动作和对象；界面入口只能证明入口存在，不等于已实测可执行。
- **有限支持**：仅支持部分对象、部分企业规模或部分动作。
- **入口型**：可以下发任务或接收结果，但不等同于业务数据接入。
- **第三方能力**：由外部产品、服务商或开发者连接器提供。

支持程度与第三方归属可以同时成立，不互相替代。未知、未展示和待授权不等于不支持；与决策相关时保留为边界或待核实项，避免删掉限制后造成能力已完备的印象。

### 4. 按用户任务与场景而不是按产品堆清单

有明确办公需求时，优先按以下用户任务组织；其他产品按其真实任务替换，不照搬办公分类：

- 聊天：消息入口、行动项、任务下发、结果回传；区分聊天入口和聊天数据访问。
- 会议：创建、查询、日程、参会人管理；单列录制、转写、纪要和写回是否支持。
- 文档：创建、编辑、协作、表格、幻灯片、内容检索、权限和版本。
- 邮件：收发、搜索、线程汇总、文件夹、附件和正式发送。
- 日程与待办：查询、创建、更新、提醒、参与人和状态写回。
- 知识：搜索、引用、创建、导入、更新追踪；不要把不同知识产品合并成一个统一知识库。
- 项目与研发：需求、缺陷、任务、迭代、工时、代码、Issue、MR、流水线和发布状态。

职能场景作为并行场景单列，不混入通用办公或核心产品能力。第三方能力标在“能力归属”中，并保留产品官网或官方平台地址。涉及内部产品对标时，使用用户实际产品名称，不用相近但错误的产品替代。

### 5. 先写结论，再补能力表

推荐正文顺序：

1. 核心结论：按问题复杂度给出定位、能力结构、覆盖强弱和决策启示，不凑固定条数。
2. 产品与开放能力：根据产品实际情况说明插件、连接器、API、MCP、Skills、消息入口或其他扩展机制各自解决什么问题。
3. 场景能力全景：表达“核心能力 → 开放能力 → 场景 → 成果”的关系。
4. 主场景能力盘点：优先写用户关注的任务，并按能力强度或状态排列；办公产品可采用下述办公任务框架。
5. 次级场景：确与本轮相关的补充或低频场景；涉及第三方时明确归属。
6. 对标与差异化：只保留对决策有用的差异化结论，不重复前文能力清单。
7. 附录：关键界面、来源链接和必要的官网地址。

正文各模块承担不同职责：核心结论回答“所以是什么”；能力表回答“有哪些”；全景图回答“如何关联”；对标回答“应该怎么做”。如果两个模块回答同一个问题，合并或删除其中一个。

## 重点判断框架

### 开放能力

当产品存在开放平台、插件、连接器、API、MCP 或技能机制时，将开放能力拆成三层；没有这些机制的产品不强行补写：

| 层 | 关注点 | 不要混淆 |
|---|---|---|
| 工具接入 | 插件、连接器、MCP 配置、MCP Hub、自定义连接器、开放 API | 工具可发现不等于已授权可用 |
| 方法复用 | Skills、任务模板、提示词、执行步骤和交付要求 | Skill 是任务方法，不是业务数据连接器 |
| 入口复用 | 企业微信 Bot、微信 Bot、QQ Bot、元宝等消息入口 | 消息入口不等于平台数据接入 |

分析其他产品或 Agent 是否可以复用某项能力时，结论至少拆为：标准是否开放、服务是否独立部署、是否需要凭证、权限和限流由谁管理、是否依赖目标产品私有实现。不要因为某产品有市场或 Hub 就声称其他产品可以直接复用其全部连接器；只有符合标准、可独立访问且完成授权的服务，才可能被多个兼容客户端接入。

### 生态归属

在正文中明确区分：

- **官方产品能力**：源产品自己的公开能力。
- **目标产品接入能力**：目标产品已提供的具体插件、连接器、API 或动作。
- **第三方连接器能力**：服务商、开发者或合作方提供的连接器。
- **消息平台集成**：通过消息下发任务，不代表源平台业务数据已接入。

第三方产品官网放在表格或附录，不把第三方来源包装成腾讯生态能力。若截图只能看到目录项，则文案使用“目录中出现”“当前连接器展示”等短句，不写成官方合作或生态复用结论。

### 内部产品或竞品对标

差异化分析优先从数据关系出发，而不是简单比较连接器数量：

- IM：讨论、决策、行动项和参与角色。
- 知识库：权威事实、文档、版本、时效和责任人。
- 项目管理：需求、任务、项目状态和交付计划。
- 代码库：Issue、代码、MR、流水线和交付状态。

重点判断关键数据是否具备统一对象关系、权限感知检索、来源追溯、版本时效和跨源关联。场景建议应从这些数据关系和用户任务中选择；只有主体确实是 Agent 产品时，才进一步分析任务编排、工具调用和自动执行，不要先罗列通用 Agent 功能。

## HTML 输出规范

仅在交付范围包含 HTML 时应用以下规则；已有构建脚本本身不扩大用户的交付要求：

1. Markdown 与 HTML 同时交付时使用一个内容源；已有构建链则复用，单页可直接生成，不为一次导出强加脚本工程。
2. 沿用用户指定的样式和现有规范；无约束时采用易读的系统中文字体、克制配色和清晰表格。
3. 首屏突出核心结论；适用的能力表、场景和对标建议按决策重要性排列。
4. 页面章节标题稳定、目录可跳转，表格在窄屏可横向滚动，图表不遮挡文字。
5. 全景图只表达一条核心关系链，节点数量控制在可读范围内；优先使用 SVG 或结构化图，不使用无关装饰。
6. 截图必须辅助说明本次分析问题，优先保留产品入口、关键能力、连接器/MCP Hub（若存在）和代表性场景；删除无法支撑结论的截图。
7. 截图图注只写产品名和能力结论，不写“证明了什么”“如何核查”或长篇证据解释。
8. 官网、官方文档和第三方产品地址使用可访问的 canonical URL；链接失效或与结论无关时删除。
9. 页面底部只保留信息截止时间和来源类型，不在正文反复解释资料来源。

## 重复与逻辑检查

交付前逐项检查：

- 标题下是否还有一段与“核心结论”表重复的总述。
- 开放能力清单与全景图是否重复堆砌同样的文字；清单讲能力，图讲关系。
- 办公、人财法、补充生态是否各自有清晰边界，是否出现同一产品跨模块重复描述。
- 章节是否服务于当前决策，是否有不适用的办公、生态或对标章节。
- 是否把入口、目录项、第三方连接器或开放 API 误写成已完成的业务接入。
- 是否保留了用户指定的主体产品、真实产品名称和最新本地内容。
- 是否仍有“调研过程、验证过程、证据分析、截图说明过程”等不适合内部汇报的文字。

## 交付前验证

对 Markdown：

- 检查标题层级、表格列数、链接地址和全景图语法。
- 搜索过时产品名、错误归属、重复章节和过程性词语。
- 确认每项能力都有归属和边界，尤其是企业微信、MCP 和第三方职能能力。

对 HTML：

- 有构建脚本时执行构建并检查结果；直接生成时检查实际 HTML 结构与资源引用。
- 检查核心标题、全景图标签、截图数量和来源链接是否存在。
- 检查旧标题、旧截图、旧能力标签和失效占位内容是否消失。
- 检查首屏主结论是否明显高于附录，移动端表格和 SVG 是否可滚动。
- 若浏览器策略允许，检查桌面与移动视口；若本地 `file://` 页面被浏览器策略阻止，只做静态结构检查并说明限制，不绕过策略。

## 回归用例

### 用例 1：前置规划与确认

输入：一个主体不明确、没有目标读者、也没有说明对标对象的请求：“帮我分析一下这个产品”。

期望：主体无法识别时先问清主体；已有可识别资料时可读取确认事实，不把目标读者等所有字段变成启动条件。仅阻断依赖未决选择的结论，其余工作继续。

### 用例 2：通用产品能力盘点

输入：一个 CRM、ERP、硬件或内容产品的能力盘点需求，没有提及 Agent、MCP 或 Skills。

期望：按照该产品的真实能力、用户任务、数据对象、流程和商业边界组织材料，不强行加入 Agent、MCP、Skills 或消息入口章节。

### 用例 3：生态与办公能力盘点

输入：一个包含目标产品目录、办公产品截图、开放平台页面和办公场景需求的长文档。

期望：先输出调研范围和能力分层，再输出核心结论、办公场景能力表和一张能力全景图；区分产品接入、消息入口和第三方能力；不把目录项写成官方生态能力。

### 用例 4：严格核对职能能力

输入：某平台连接器写有文档和消息，第三方 HR 连接器写有考勤绩效，用户要求核对是否支持考勤查询。

期望：平台连接器表格删除考勤查询；考勤绩效只保留在第三方 HR 能力中，并标记第三方；不使用通用开放 API 能力补齐结论。

### 用例 5：内部汇报收敛

输入：一份包含研究过程、重复结论、七张截图和多层解释的 Markdown。

期望：保留能支持决策的主结论，删除重复过程叙述和低价值截图；首屏突出总结，附录保留必要来源和截图；构建 HTML 后截图和图注数量减少且与分析问题直接相关。

### 用例 6：输出边界

输入：用户只要求分析，不要求修改文件或生成 HTML。

期望：直接输出分析结论，不创建文件、不启动服务；只有当前任务包含文件交付或修订时才修改相应文件；已有 HTML 构建链不自动授权生成 HTML。
