# 产品走查

本 Skill 持有走查上下文门、证据交接和范围内主结论阈值。它决定检查范围与专业分工；专项 Skill 提供专业方法。确认与执行边界遵循 [团队工作流](../../workflow.md)，产品模型及回写遵循 [项目记忆规范](../../project-memory-rules.md#轻量产品模型与回写)，此处不另设确认轮次或保存规则。

## 何时使用

用户要求“打开应用走查”“走查产品”“检查应用流程”“走一遍 usecase”“检查产品文案和逻辑”时使用。截图、单句文案或纯视觉问题直接采用相应专项方法，不强制走完整产品流程。文档或设计稿评审如需正式主结论，只引用本文件的判定规则，不因此启动应用取证。

## 走查深度与上下文门

先判断本次需要回答什么，再核对相应上下文：

| 档位 | 内部核对维度 | 主要检查 |
| --- | --- | --- |
| 视觉/布局/单句文案 | 目标页面或文案及可见证据 | 视觉层级、布局、表达和可见适配 |
| 局部交互/局部状态 | 受影响页面、用户任务、入口、完成结果 | 受影响路径、反馈、状态与恢复 |
| 产品文案与逻辑 | 用户、场景、目标、价值、范围/版本及受影响规则、权限和风险 | 产品闭环、业务规则、权限、异常和文案承诺 |

这些维度用于内部判断，不是完整问卷。先使用当前项目有效的已确认上下文，只补会改变本次判断的缺口；不适用的维度无需提问。局部任务仅核对受影响的角色和规则，不扩展为全产品访谈。usecase 能说明操作路径，但不能自动证明目标、价值或业务规则已确认。

没有产品背景却要求产品逻辑走查时，先以最少问题明确服务谁、完成什么任务、何为成功和本轮范围；缺口涉及的判断待答案后进行，独立资料核对可继续。已有足够明确的背景时直接取证。用户明确要求“先看再说”时，可取证并给出受限分析，结论仍按证据阈值判断。

## 执行与证据交接

1. **界定任务**：识别对象、入口、指定路径、检查深度与本轮成功条件，依上节判断关键背景是否充分。
2. **确定一个取证入口**：由本 Skill 指定本轮执行方，统一维护范围、路径和证据索引；按下一节选择可用方式。
3. **分配专业问题**：页面取证与可用性可采用外部审计方法；产品规则交给产品思考，视觉证据交给视觉评审，代码可见文案交给可用的文案审计。具体能力与路径见 [能力矩阵](../../capability-matrix.md)，不默认加载全部专项。
4. **交接与合并**：输入为已确认上下文、受影响范围、路径、证据索引和待回答问题；返回发现、对应证据、实际检查范围和未验证项。合并同一位置及根因的发现，保留专业依据，按下节给出主结论。
5. **交付**：按输出结构汇总；后续修订、复验与回写执行共享工作流及记忆规范。

下游复用本轮可接受的证据，不再次启动父级或本 Skill 的整条编排。仅在证据缺失、失效、状态变化或所用方法要求重采时补采。新发现的关键背景缺口返回本入口统一处理。

截图须注明来自用户素材、历史材料还是本轮操作，必要时保留时间与版本；不能冒充本轮运行证据。外部审计的步骤健康状态属于局部证据，不覆盖本文件定义的范围内主结论。

## 取证方式与降级

- **外部审计方法和操作工具均可用**：实际读取所选外部 Skill 及其对本任务强制要求的引用，完成前置动作后采用其流程。以读取到的规则为准，不凭能力目录或本文件摘要声称已加载；同一版本已读取内容可复用。读取路由规则不等于再次启动父级编排。截图可由该流程采集，不要求启动前已有截图。
- **外部审计方法不可用，操作工具可用**：直接走指定路径，保存并检查关键状态的运行证据；不声称执行了缺失的外部 Skill。
- **必要依赖或取证能力受阻**：停止受阻分支，说明具体未覆盖步骤；以现有截图、代码或资料完成可支持的静态/受限检查。缺少外部方法不等于缺少操作工具，不能自动放弃仍可完成的取证。

采用外部 Skill 时遵循其证据限制；必需依赖不满足则不声称完成该方法。任何降级的结论均限于实际获得的证据。

## 主结论与证据阈值

本规则适用于应用走查和文档、设计稿、原型等评审。先声明评审对象、范围、成功条件与验证层级，再按以下顺序判定；表中的“必要项”由本轮目标和已确认要求决定，不要求每次检查全部产品能力。文档评审的证据可为需求条目及逻辑关系，不能据此宣称真实实现或用户效果通过。

| 主结论 | 判定条件 |
| --- | --- |
| 暂不通过 | 已有证据确认本轮核心目标不能成立、存在严重权限/数据风险、违反已确认关键规则，或必要验收项失败。其他证据缺失不能掩盖该失败，仍列出未覆盖项。 |
| 证据不足 | 未发现上述已确认失败，但关键上下文或必要项的证据不足，无法判断是否满足本轮成功条件。缺少工具、版本、角色或规则均可能造成此状态；不能以假设补成通过。 |
| 条件通过 | 核心目标与必要规则已有证据满足，仍有需修复但不阻断本轮目标的已知问题；说明影响、修复条件与复验责任。不能将核心目标待验证、权限待确认或严重问题未修复作为放行条件。 |
| 可用 | 本轮必要项已覆盖、成功条件成立，无本轮要求修复的已确认问题；可保留可选改进。未要求检查的能力不在结论范围内。 |

问题严重度与主结论独立：红为核心阻断或严重风险，黄为重要但非阻断的问题，绿为轻微问题或可选改进；依据影响，不按数量定级。证据缺口表示未知，不按绿色或低风险处理。没有发现问题时直接说明，不为填充报告生成建议。

验证层级为“产品规则 / 原型 / 实现 / QA / 真实用户”，仅报告本次适用层及其已检查范围、待验证内容或不适用原因。截图只支持可见状态，一次走查不自动代表所有层级通过；产品推演、静态视觉结论不能替代真实流程、实现或用户验证。

## 输出结构

按本次范围简洁交付，空分类可省略：

- 对象、范围、成功条件、入口或路径以及上下文缺口；
- 范围内主结论及证据依据；
- 按优先级排列的发现：位置/步骤、证据、用户影响、规则或原则依据、建议；
- 未验证项、限制及适当的后续验证责任。

方案文案审查与代码来源追踪分别说明实际采用的方法及范围；页面缺陷不直接上升为业务事实。最终成果归档和基线写入均按项目记忆规范处理。
