# 产品与交互思考

围绕用户任务、产品对象、路径、状态、规则、边界和验收形成可执行方案。需求分析聚焦产品行为；只有任务包含视觉设计时才展开风格、配色或设计语言。

本 Skill 提供专业方法，不另建确认流程或项目事实库：

- 阶段推进、澄清及授权判断遵循 [团队工作流](../../workflow.md)。下列方法按任务选用，无需逐步向用户复述或等待。
- 轻量模型、事实分类和回写统一遵循 [轻量产品模型与回写](../../project-memory-rules.md#轻量产品模型与回写)，包括用户授权范围内决策的记录方式。
- 真实应用取证由 [产品走查](../product-audit/SKILL.md) 编排；从该入口进入时接收其范围、上下文和证据，不再次启动上游。
- 文档就绪性使用 [主结论与证据阈值](../product-audit/SKILL.md#主结论与证据阈值)，按下文的文档证据映射应用，不把文档推演写成真实应用验证。

## 方法选择与参考资料

| 当前任务 | 使用方法 | 按需读取 |
| --- | --- | --- |
| 方向讨论、功能构想 | 一：方案思考 | [示例](references/examples.md)，仅在需要校准深度时 |
| 完整产品方案、功能方案 | 一：方案思考 → 二：路径与边界 → 四：需求审查的适用维度 | 深度与澄清按[完整方案规则](../../workflow.md#完整方案的深度与交互选择)；涉及交互读取团队交互规约 |
| 用户路径、首次使用、边界分析 | 二：路径与边界 | [示例](references/examples.md) |
| 撰写 PRD | 三：需求文档 | [PRD 标准及模板](references/prd-output.md) |
| 审查已有需求、PRD 或交互方案 | 四：需求审查 | [交互原则](references/ux-principles.md) 中适用的判断依据 |
| 生成测试用例 | 五：测试设计 | [示例](references/examples.md)，仅在需要校准深度时 |

写 PRD 时使用需求审查维度做内部检查；审查用户提交的材料时则明确本轮评审对象、版本与范围。两者不混称为独立审查。

需要图表时调用 [结构化图表](../product-team-diagrams/SKILL.md)，图型选择、布局、渲染与质量检查均由其维护。产品方法只确定要回答的问题：任务分支用流程或决策图，对象生命周期用状态图，多方交互用时序或协作表达，模块和权限边界用架构表达。文字或短表足够时无需生成图表；需要语义示例时读取 [产品图表示例](references/diagram-patterns.md)。

## 一：方案思考

开始前按[产品分析前置判断](../../workflow.md#产品分析前置判断)明确决策用途、真实问题、成功判断、参与者与约束；沿用共享的缺口分类和推进条件，不另设确认流程。

1. **提取问题。** 从现有上下文识别产品、目标用户、用户任务、当前障碍和限制，把需要决策的问题说清楚。
2. **补充依据。** 同类方案能影响当前决策且具备资料时开展调研，解释相关产品做了什么选择、理由和适用条件；无法核实的内容保留其证据状态。
3. **形成方向。** 按问题复杂度比较核心实现、差异化方向或异常导向的替代方案，不凑固定数量。每个方向说明用户价值、成立前提和主要风险。
4. **给出推荐并展开。** 方向建议说明取舍及范围；完整产品方案或功能方案继续执行“二：路径与边界”，将核心任务的阶段操作写入方案，再用“四：需求审查”的适用维度检查。按团队工作流处理交互选择、逐步检查和方案后的可选场景核对，不以方向推荐代替完整方案。已明确要求直接进入 PRD 或 Demo 时按工作流继续。

存在关键假设、难以恢复的后果，或用户要求挑战方案时，可内部使用“方案收益 / 风险挑战”双视角分析。围绕事实检验用户价值、研发可执行性及假设失效的后果，最后给出统一推荐和待验证项；无需输出角色对话或制造分歧。

## 二：路径与边界

以具体用户任务为单位，识别触发、入口、前置条件、动作、系统反馈和完成结果。检查首次进入、必要对象创建、加入已有对象、已有数据状态及再次进入，避免直接从熟练用户的首页开始。

按适用性检查以下边界，并关联到受影响的路径节点：

| 类别 | 检查内容 |
| --- | --- |
| 输入与数据 | 空状态、不完整数据、非法输入、极值、对象已失效或已删除 |
| 网络与系统 | 慢网、失败、超时、结果未知、部分成功 |
| 用户行为 | 中途退出、恢复、重复提交、撤销、并发操作 |
| 权限与访问 | 角色差异、对象归属、可见与可操作范围、途中失去权限 |
| 通知与异步 | 任务进行中、返回查状态、消息延迟、数据过期 |
| 生命周期 | 创建、变更、归档或退出，以及适用的删除与恢复 |

对每个重要边界记录触发条件、系统处理、用户反馈和恢复结果；依据当前范围排优先级。并非每个产品都需要每种能力，未纳入范围的能力不能凭边界清单自动新增。

输出路径或图后，说明不明显的交互取舍和实现前提。图示只表达方案，不能充当研发确认或运行证据。用例采用明确、可验证的书面语言，说明执行主体和动作对象，避免“系统处理后完成”等空泛概括。

## 三：需求文档

读取 [PRD 标准及模板](references/prd-output.md)，按本轮范围组织文档；模板是内容覆盖工具，不是必填问卷。

1. **整理输入。** 关联功能与版本、背景证据、用户任务、范围、权限、约束、依赖及适用的指标和发布要求；沿具体案例梳理入口、关键阶段、状态与完成条件。资料状态及未决项处理遵循前述共享规则。
2. **写清行为。** 需求原子化，连接触发条件、系统行为、用户反馈和可观察的验收结果。适用的核心链路及阶段交互规格按参考模板记录，保持需求、规则与验收可追踪。
3. **内部检查。** 使用下一节的六个审查维度；另外核对关键需求是否可测试、已用图表是否准确、功能描述是否具体。先修复有依据且在授权范围内的问题，再报告剩余限制。
4. **交付。** 提供本轮要求的文档与简明内部检查结果。必要时列出已修复项、未决问题及其影响；不重复整份正文，也不宣称共同生成的文档已经独立审查或实现验证。

## 四：需求审查

针对已有 PRD、需求描述或交互方案检查本轮适用内容，不因请求局部交互评审而扩展为全产品审计。

| 维度 | 判断重点 |
| --- | --- |
| 逻辑完整性 | 核心任务能否完成；进入、中间、退出、异常状态及必要恢复是否闭合 |
| 研发可执行性 | 行为能否衡量；矛盾、隐式依赖、数据边界、接口前提及权限规则是否可定位 |
| 范围清晰度 | 本期范围、非目标、后续项和优先级是否足以约束实现 |
| 用户可见文案 | 按钮、空态、成功、失败、处理中、权限受限等反馈是否匹配真实能力，是否有下一步 |
| 交互与体验 | 关键动作是否明确、反馈是否及时、失败是否可恢复，首次及重复使用是否覆盖 |
| 一致性 | 业务规则、术语、文案及交互是否与已有规则一致，差异是否有依据 |

文案检查针对方案内容；只有实际执行代码文案审计后才能声称检查了来源及展示链路。视觉风格评审交给对应专项 Skill。

### 文档证据映射

主结论、严重度及证据缺口的判定统一使用 [主结论与证据阈值](../product-audit/SKILL.md#主结论与证据阈值)。对文档审查，按以下方式解释其中的证据和必要验收项：

- **判断对象**是指定版本文档在本轮范围内能否支持所要求的下一阶段，必要项来自已明确的交付目标和适用规则。
- **可观察文档缺陷**包括能定位的矛盾，以及本轮明确必需的任务、权限、责任或验收规格缺失。缺失本身可成为文档阻断证据，无需先证明真实系统也失败；说明缺失位置和为何影响当前交付。
- **证据未知**包括只收到片段而无法确认是否缺失、关键上下文不足或关键前提未经验证。不得把未知自动解释为文档缺陷，也不能凭“应该已有实现”放行。
- **模板差异**本身不是缺陷。标题、顺序或非适用章节的省略不等于必要规格缺失。
- **结论范围**限定在材料和实际检查层级；文档缺陷不表示真实系统已失败，用户接受风险也不等于问题已修复。

### 报告内容

结论在前，说明对象、版本、范围和依据，然后按实际问题提供：

| 问题位置与证据 | 影响及严重度 | 建议修法 | 条件或复验要求 |
| --- | --- | --- | --- |
| [章节、规则或原句] | [受影响任务及后果] | [具体改法及取舍] | [验证方式，适用时填] |

未验证范围另列，避免与已观察缺陷混在一起。简单审查用短段落即可；复杂审查可按上述六维度分组。未发现问题时直接说明，不凑优化建议。

## 五：测试设计

从功能、角色、当前范围和已定义验收结果生成用例，保持与需求或规则的对应关系。生成用例不表示已经运行测试。

```text
TC-[编号] [描述性名称]
关联需求或规则：[已有 ID 或具体位置]
前置条件：[角色、起始数据、权限及状态]
操作：[可复现步骤]
预期结果：[可观察的反馈、数据与状态变化]
类型：正常路径 / 边界情况 / 错误状态 / 反向用例
优先级：P0 / P1 / P2
```

覆盖主路径及适用的其他路径、空或零数据、边界值、非法输入、断网、权限差异、重新进入、并发与异步结果。预期依赖未决规则时标明待定及关联问题，不以猜测补成验收事实。

优先级按失败对核心任务、权限、数据和恢复成本的影响判定，不凑 P0 数量。沿用本轮适用的上线标准，区分“测试优先级”与“已定义的发布阻断条件”；交付用例及覆盖限制。
