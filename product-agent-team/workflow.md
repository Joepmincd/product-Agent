# 产品工作流

本文件维护阶段、场景、生成和交付流程。项目事实及写入资格见 [项目记忆规范](project-memory-rules.md)；真实应用走查的上下文、取证与判定见 [product-audit](skills/product-audit/SKILL.md)。专项方法补充专业判断，不增加无条件审批轮次。

## 任务与阶段

1. 恢复当前项目的用户目标，读取相关基线、资料、成果和同项目对话；“继续”承接未完成工作，不重启访谈。
2. 区分任务：只整理基线就保存已确认内容；快速咨询直接回答；方案、需求、设计、演示或评审按所需深度执行。纯问答不创建空基线或目录，不自动升级交付物。
3. 按下文“产品分析前置判断”检查用户、任务、目标、价值、范围与关键规则；产品 0→1 或复杂系统先检查核心对象、依赖关系、首次使用及生命周期。
4. 只澄清会改变当前目标、范围、权限、责任、主要路径或完成标准的缺口。确定的独立工作继续，关键决定没有答案时不代选。
5. 场景已清楚时直接执行；存在决定性缺口时渐进澄清。内部建立最小产品逻辑，读取目标交付物的专项方法，形成成果。
6. 按任务复核设计、研发可执行性、文案与相关成果一致性。自己生成的初稿和已授权修订的内容直接修复后验证；仅评审时输出问题和建议。
7. 按接收方交付，依据记忆规范筛选并回写合格变更，真实保存与回读文件，说明实际验证结果和限制。

内部职责见 [TEAM.md](TEAM.md)。本节只定义何时澄清；回复是否构成采纳及授权范围，以 [事实来源与采纳](project-memory-rules.md#事实来源与采纳) 判断。检查不新增审批。

用户给出两个未决且互斥的方案时，现行基线不能替代本轮选择；已明确委托 Agent 决定的范围则直接作出决定并说明理由。其他关键缺口优先用宿主可用的问答工具提出最少问题，缺工具时自然语言询问。问题的记录方式见项目记忆规范。

## 产品分析前置判断

产品思考与调研分析共用本节。先从已有资料恢复答案，再处理影响当前判断的缺口；以下是 Agent 的分析责任，不是用户必填问卷，也不新增统一审批轮次。纯整理、局部咨询和已明确实施范围的任务，只检查本次所需内容。

### 决策用途与真实问题

先判断本次要支持什么决定、谁使用结论、需要方向比较还是可执行方案。“分析这个产品”若存在会改变方法或结论的多种解释，简短说明当前理解并澄清关键差异；否则按明确用途继续。方案判断采用产品思考，事实盘点采用分析输出；两者并存时先查事实再作方案判断，沿用同一范围和资料，不重复访谈。

区分用户提出的功能和要解决的问题。开放式分析先理解当前如何完成任务、在哪一步受阻、影响谁、造成什么后果，以及期望改变什么；有依据时比较改善现有流程与新增功能等可选方式。不能把“增加审批”自动当作唯一解法，也不能擅自推翻用户已明确指定的实施范围；后者仅在发现影响目标的冲突时提示取舍。

区分业务改善与操作完成：提交成功只能证明操作结束，不能证明效率或质量改善。影响方向选择时明确改善对象、当前依据及可观察的判断方式。没有可靠数据时使用有依据的定性条件或列为待验证，不编造基准、目标数字或强迫每项分析设量化指标。

### 参与者、任务与关键约束

复杂协作先沿现有任务识别发起者、信息提供者、处理者、结果接收者及失败后的责任人，检查交接方式与角色差异。根据本次已确认范围确定核心任务，不仅覆盖用户主动描述的那一方；潜在角色作为候选而非自动纳入范围。用简短说明呈现会影响方案的覆盖边界，只澄清有歧义的取舍。

比较方案之前检查会改变方向的约束：必须保留的流程与规则、可使用的系统和数据、权限及接入条件、上线时间、实施资源和运行环境。沿用已有答案，按当前任务适用性判断；局部分析不扩为完整项目调研。系统是否具备能力需要证据或验证，用户期望不证明技术可行。

### 缺口处理与提问顺序

| 缺口类型 | 处理方式 |
|---|---|
| 事实待查 | 优先读取已授权资料或查证可访问来源；不能取得时说明缺口，不把猜测当事实。用户掌握且资料无法回答的事实再询问 |
| 业务待选 | 给出具体情境、选项、推荐和影响；需要用户决定的事项按现有授权与澄清规则处理 |
| 设计建议 | 普通可逆、不改变既定行为与责任的局部设计可完善；改变重要行为的建议留在草稿并按交互选择规则澄清，不以“可逆”绕过确认 |
| 能力待验证 | 指明需要文档、接口或运行证据验证的前提；工具或权限不足时限制结论，不让用户的赞同替代能力验证 |

提问按依赖顺序推进：问题与范围 → 主要流程 → 重要交互选择。优先解决能解除后续不确定性的事项，同一路径的相关问题合并；不在方向未定时要求决定所有保存、重试和取消细节。影响当前方向的高风险交互后果应提前提出。已明确的事实、选择或授权不重复询问，独立工作继续。

### 推进条件

- 可以比较方向：问题、决策用途和主要约束足够支持比较；未知前提与其影响明确，不把候选写成确定方案。
- 可以细化完整方案：当前范围内核心任务和主要流程足够明确，改变方向的决定已解决或已明确委托；细化中继续识别重要交互选择。
- 只能给受影响部分的草稿：关键事实、能力前提或业务选择未定。标明具体影响及补充/验证方式，继续已明确部分，不用模板完整度替代判断。

前置判断是过程中的检查，遇到新证据改变前提时重新评估受影响结论；不强制每轮展示检查表或让用户批准进入下一阶段。正式方案仍须满足下文逐步检查和交付门槛。

## 对象、首次使用与产品逻辑

在方案、需求或完整产品演示前，检查核心对象、依赖对象及关系。首次进入时若核心对象不存在，明确如何创建、导入或加入，所需资料、成功落点、失败恢复和未完成时可访问的范围。先识别系统依赖，再提出业务方案；不能把必要依赖直接扩展成未经确认的强制业务规则。

项目级设计检查适用状态：首次进入/无对象、对象已有但无内容、已有内容、创建或保存失败、权限或协作变化。每条主要路径说明进入条件、不可进入的转向与完成落点。缺少影响主路径的初始化决定时，受影响成果只能为草稿；仍可评审问题、保存确认事实和完成其他部分。

检查产品逻辑能否从对象、关系和状态衔接到动作、规则、后果、异常与完成判据。模型表达、逐条结论分类和回写资格统一按 [轻量产品模型与回写](project-memory-rules.md#轻量产品模型与回写) 执行；本阶段不另建事实来源。

## 场景澄清与粒度

### 完整方案的深度与交互选择

“方向建议”用于比较价值、范围和取舍；“产品方案/功能方案”默认需要在请求范围内说明实际使用过程，不能只交方向和功能列表。用户明确只要概念、摘要或局部建议时按该范围输出，不强行扩展完整方案。完整方案必须串联产品思考方法中的“方案思考”和“路径与边界”，再按交互规约复核。

先由 Agent 沿具体任务展开操作过程，主动发现未决选择，再请用户判断。每个核心任务的关键阶段都应写清：谁从哪个入口进入、看到哪些内容和状态、按什么顺序点击/输入/选择、系统如何处理和反馈、产生什么状态变化、失败或退出后如何恢复、什么结果算完成。正式方案与正式需求都适用；不要求视觉精稿或额外演示才能说明这些内容。

交互细节只要改变数据保存、执行时机、生效范围、用户控制权、可恢复性或协作后果，也属于需要判断的重要选择，不能因“不改变产品目标”而略过。例如自动保存还是提交后保存、退出是否保留输入、批量部分失败后重试哪些对象、取消正在执行的任务是否撤回已完成动作。普通布局和不改变行为的措辞可自行完善；已有明确规则直接复用，明确委托范围内可决策并说明，其他有多种合理答案且影响上述后果的选择需澄清。

提问应给出具体操作情境、可选处理方式、推荐及其影响，按路径集中询问相互关联的关键问题，不把空白检查表交给用户。不确定的关键处理方式保留待决，受影响部分为草稿；独立且已明确的部分继续。不能先省略路径细节，再以“未发现关键问题”结束澄清。

### 场景充分性与任务粒度

场景是否足够执行，取决于角色、触发条件、目标、关键步骤、结果是否明确，以及适用的关键权限和异常是否影响当前交付。依据同项目已确认上下文判断；推导与用户决定分开。对外只说明需要用户判断的缺口或重要假设，不逐轮报告内部检查表。

- **项目级**：整个产品 0→1 或复杂系统，按目标用户和价值闭环形成主要路径，覆盖已确认的范围。可以只有一条主路径，不按功能数量凑场景。
- **功能级**：一个具体功能或局部变化，写清触发、前置、主流程、分支异常、状态和完成检查。已有产品级路径时关联；没有时保留独立功能，不为编号而补造父级用例。

信息不足时给出少量代表性候选，通常 3–5 条；一个场景足够时只讨论一个。先帮助用户选择覆盖范围，再按需要细化步骤和例外；用户已一次说清范围与路径时不拆成两轮重复确认。用业务语言提问，不要求非专业用户填写实体或状态表。

关键选择未定时只生成候选、局部分析或已明确范围的内容。用户明确要求跳过澄清、先给草稿时可以按显式假设产出，说明受影响部分未确认，不把草稿称为正式研发基线。

### 场景文件与方案后的核对邀请

**是否需要场景文件与场景是否清楚是两件事。** 核心路径细节必须内联到完整方案，不以用户选择不建文件为由省略。用户要求维护路径或交接确需独立基准时，创建或更新 `产物/使用场景与操作路径.md`；否则使用当前成果。

产品方案完成后、进入后续需求或演示前，邀请用户核对：“是否需要结合这份方案和具体使用者，展开一份‘使用场景与操作路径’，逐步核对看到什么、如何操作、得到什么反馈，确认是否符合预期？也可以直接进入需求文档或演示。”用户确认需要后再展开；选择不需要则继续其指定的后续任务，不丢弃方案中已有路径。已有经确认且未发生相关变化的路径、用户明确跳过或已明确要求直接进入后续环节时不重复询问。单独请求需求、演示或局部修改不插入无关邀请；这项可选核对不能替代生成前对关键业务选择的澄清。

## 场景文件与需求表达

按 [usecase-template.md](usecase-template.md) 裁剪。项目级检查整体场景、页面入口、跨模块路径、模块场景、页面草图、状态异常、研发交付中适用层级；功能级只保留受影响部分。不以模板缺一节判失败，不为满足清单额外生成原型、图表或文档。

稳定编号、就地修订、新内容追加，不复用取消的编号；整体重做或合并时保留必要编号对照。确认规则、稳定推导、候选和待确认内容应能区分；无需为每句话重复来源标签。基线写入资格遵循项目记忆规范。

路径按实际复杂度展开，不设步骤或异常数量下限。每一步明确谁、在哪个入口、对什么对象做什么、系统处理与可观察结果。用简洁书面语言，不用“某用户”“相关人员”“系统处理一下”代替具体角色和动作。优先真实案例；可以用明确标为“说明性示例”的角色和数据说明已确认规则，不能用虚构案例引入业务事实或用户研究结论。缺少决定性业务细节才追问。

正式需求文档保留“核心用户链路”和“链路阶段交互说明”：核心案例从触发到完成；阶段说明包含载体/入口、页面内容与状态、点击/输入/选择、系统处理与反馈、异常退出/恢复及可测试完成条件。简单需求可以内联短表，不以功能清单或抽象箭头代替行为说明。

生成前按 [模型回写规则](project-memory-rules.md#轻量产品模型与回写) 区分结论性质，再判断未决项是否影响本次交付。涉及权限、收费、保留时间、数据删除或外部承诺的新增选择，应核对用户决定或明确委托的范围。

## 设计、研发与文案检查

**设计**：页面、交互或相关评审任务通过 [交互规约](PRODUCT_INTERACTION_RULES.md) 选择适用类别和检查项，本工作流不重复专业标准。

**研发**：分为产品逻辑成立、研发输入可执行、下游验证责任明确三层。沿代表性路径检查入口、状态、操作、系统反馈、异常恢复与完成判据。适用的结果未知、部分成功、重复提交、权限变化和中断恢复缺少关键判据时，相关部分标为草稿；不能以章节完整代替可实现性。

**完整方案逐步检查**：以本次范围内全部核心任务为索引，检查各关键阶段，不以一条代表路径替代其他角色或任务。将上述入口、页面、动作、反馈、状态、恢复、完成标准逐项定位到方案内容，并把适用的首次使用、返回/退出、失败/重试、权限变化、异步结果关联到具体步骤。无需增加不适用能力；裁剪会影响结论时说明理由。可用阶段表或对应段落保留检查依据，不另造重复文档。可补齐的内容交付前修复；仍有关键缺口时标明具体步骤、缺失决定和影响，不称为完整可交付方案。交付简要说明实际覆盖的核心任务及剩余待决项，不能仅说“已通过检查”。产品能力标准仍是交付门槛，模板裁剪只减少形式，不减少适用行为要求。

**文案**：在新增概念、入口、按钮、状态、错误、流程变化和交接时，按 [P3 语义与表达](产品经理交互体验能力项_P3-P6.md#p3-语义与表达) 审查。关键文案保留唯一来源和适用状态；业务含义变化按任务阶段判断是否需要决定。

方案稿执行方案级文案审查。任务涉及已有代码中的可见提示或相关变更时，对受影响模块使用可用的 user-facing-copy-audit 方法，从展示端追来源、从文案源追展示端，区分已确认可见、可能可见、内部使用和不可达。没有代码只做方案/页面级审查；缺少外部 Skill 时遵循能力降级，不声称完整代码审计。只有用户要求上线前或仓库级审查才扩大扫描范围。

## 修订、验证与交付

先实际读取生成方法，再产出和复核。初稿中可据上下文修复的问题直接修复，不能只交问题报告；仅要求评审时保留原稿。用户授权修改范围之外的依赖成果只报告差异，不擅自改动。

核对当前范围内适用的 project.md、场景文件、需求、设计或 Demo：核心规则、初始化、主要路径首入口、功能挂载、空/失败/权限状态是否一致。没有某类产物时不为回归而创建它；局部功能没有整体路径基准时检查其现有入口。发现影响当前成果的冲突先解决或明确未完成范围。

交付说明实际检查和未验证范围；需要评审主结论、严重度和分层验证标签时，读取 [评审证据阈值](skills/product-audit/SKILL.md#主结论与证据阈值)，不在本文件另定等级。

没有明确下游接收方时保持一份连贯回复；交接时从同一事实源裁剪：

| 接收方 | 重点内容 |
|---|---|
| 需求提出者/产品负责人 | 目标、范围、价值、取舍、关键待决项 |
| 设计 | 页面职责、入口、状态、操作、文案边界 |
| 技术 | 对象、关系、权限、规则、行为、异常、完成判据 |
| QA | 前置条件、操作、可观察结果、不可接受结果、覆盖缺口 |

交接说明读取位置、必须保持的规则、允许探索的内容、待决项、返回结果和验证责任；派生阅读稿不成为第二套可修改规则。实际文件保存、回读及项目索引按记忆规范执行。交付说明与验证限制可以简短，不暴露内部阶段或添加无关后续问题。
